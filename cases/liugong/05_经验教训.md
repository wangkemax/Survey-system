# 柳工配件库项目 · 经验教训

> 这是案例库里最有价值的部分。每条教训都是真金白银踩出来的。

---

## 经验 1：业主说的"JIT"未必是真 JIT

**场景**：客户描述业务时反复说"JIT 配送占 60%"。
**问题**：差点按"4 小时级即时响应"设计方案，结果方向全错。
**教训**：一定要追问**订单时窗**。柳工实际是"提前 3 天下单、当晚做次日单"——这是**次日波次拣选**，不是即时配送。问法：「客户下单到要求送达，中间隔多久？」

## 经验 2：问"日均订单"前，先确认口径是单/行/件

**场景**：上午调研填"日均订单 1000 单"，下午半月数据却是 549 单/15 天 ≈ 37 单/日。
**问题**：两个数字差近 30 倍，险些按 1000 单规模配置 AGV（多花几百万）。
**教训**：报数时必问「这个数是订单数、订单行数、还是件数？」。三者可能差一个数量级。
- 真实：549 单 / 9800 行 / 27545 件（半月）= 37 单 / 653 行 / 1836 件（日）

## 经验 3：平均件数掩盖业务结构

**场景**：算出"平均 2.8 件/行"，以为是普通拆零。
**问题**：实际内部分化严重——3 号线"基本一单一件"，被平均值掩盖。
**教训**：不要只看平均值，要按**产线/客户/品类**拆开看分布。

## 经验 4："一单一件 + 看批次"是最难的业务形态

**场景**：柳工 1/2 号线不看批次，3 号线必须按指定批次出库 + 基本一单一件。
**问题**：错件代价极大（整单作废），不能用标准货到人方案一刀切。
**教训**：这类业务必须**物理隔离 + 专车专用 + 双重扫码 + AI 视觉批次识别**。方案上把 B 区拆成 B1（普通）+ B2（批次锁定）。

## 经验 5：核实"面积/SKU"的口径——别把不相关业务算进来

**场景**：说明书写"8,121㎡ / 7,374 SKU"，实际本仓库只有 4,387㎡ / 6,800 SKU，另一半是别的业务线，不在项目范围。
**问题**：按 8,121㎡ 做了方案，投资多估了约 280 万。
**教训**：开工前必须确认"**本次项目范围内**的真实面积和 SKU"，别被文档里的总数带偏。

## 经验 6：租赁/通用仓库，优先可迁移设备

**场景**：客户希望方案能复制到其他仓库。
**问题**：若上 ASRS，搬迁残值率 ≤ 30%，等于打水漂。
**教训**：优先 **SLAM 激光 AGV（不打地面）+ 螺栓装配货架（可拆装）+ 软件（100% 可迁移）**。投资分"软件层/设备层/改造层"，改造层尽量小、尽量可逆。

## 经验 7：不要为"对标灯塔工厂"而上 ASRS

**场景**：客户有"对标灯塔工厂"的形象诉求。
**问题**：7000 SKU + 长尾极重 + 拆零拣选——ASRS 的"高密度单元化"基因完全不匹配。
**教训**：用**分品类分区**的混合方案。每类 SKU 用最匹配的技术，不强行上单一高大上技术。

## 经验 8：物理调研要查"业主方改造许可"

**场景**：地面不允许自流平、不允许打孔。
**问题**：若没提前问，方案里写了磁条导航 AGV，落地时才发现做不了。
**教训**：物理调研必含"业主方改造许可"清单：地面打孔、自流平、墙面附挂、电气增容、网络布线、退场处置。

## 经验 9：月台高度 0mm 是隐藏成本

**场景**：4 个卸货门都是平地式，无高位月台。
**问题**：AGV 无法直接对接货车，需加装登车桥。
**教训**：现场量月台高度，没有就把"液压登车桥"列进预算（4 个约 32 万）。

## 经验 10：与客户系统对接，先问"共享了什么数据"

**场景**：客户说"与 MES 有 API 实时接口"，听起来很完善。
**问题**：实际只共享"订单"，库存/发货/批次/CID/工位/质量都没接通。
**教训**：问"API 通"还不够，要问「**具体共享哪几类数据**」。本仓库是柳工内部系统对接（非跨公司），扩展难度低但工作量不小。
